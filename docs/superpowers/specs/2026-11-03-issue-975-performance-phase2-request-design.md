- 이슈: https://github.com/TEAM-ROMROM/RomRom-FE/issues/975
- 원칙: 화면 동작은 그대로, 호출 수·재빌드·깜빡임만 줄인다. 서버 변경 없음
- 범위 밖: 홈 피드 차단 반영(다른 작업), 채팅방 화면 본체·메시지 위젯

## 1. 보낸 요청 재조회 조건

| 원인 | 설계 |
|---|---|
| 요청관리 탭이 `myItemsProvider` 변경마다 `loadForItems` 호출 > 보낸 요청을 카드 수만큼 매번 재조회. 홈·등록·마이페이지 당겨서 새로고침, 홍보, 수정 등 카드 구성이 같은 변경에도 N회 호출 | `loadForItems`에 보낸 요청 조회 조건 추가: **마지막 전체 조회 카드 목록과 다를 때** 또는 **강제(`isSentReloadForced`)** 일 때만. 받은 요청(현재 카드 1회)은 지금처럼 매번 조회 |
| 같은 카드 목록이어도 보낸 요청 카드에 보이는 값 = 내 물품 대표 이미지 | 화면이 카드 대표 이미지 변경을 감지하면 강제 조회 |
| 요청관리 당겨서 새로고침 | 강제 조회. 내 물품 변경 리스너가 먼저 시작한 로드(받은 요청만)에 합류하고 보낸 요청 조회만 덧붙임 (받은 요청 중복 호출 없음) |

- 보낸 요청이 바뀌는 다른 경로(전송·거래 방식 수정·취소·정렬·다시 시도)는 기존대로 notifier 안에서 재조회
- 상대 수락·취소 반영: 요청관리 탭 진입(`currentTabIndexProvider` 구독)·앱 복귀(요청관리 탭 표시 중)마다 `reloadSentIfStale` 백그라운드 재조회 (로딩 표시 없음, 마지막 전체 조회 시작 후 10초 미만·첫 로드 전 생략)
- 재조회 판단(카드 목록 비교·최소 간격)은 순수 로직 `SentRequestsReloadPolicy`(`lib/utils/`)로 분리
- 채팅 거래완료 거절·거래완료: 내 물품 재조회에 기대지 않고 `reloadReceivedAndSent` 직접 호출
- 같은 카드 목록에서 이전 조회 일부 실패 > 자동 재조회 안 함 (배너·다시 시도 유지, 당겨서 새로고침은 강제 조회)

## 2. 받은 요청 카드별 캐시 (stale-while-revalidate)

- notifier 내부 캐시 `카드 ID > 받은 요청 목록` (최신 차수 응답만 저장, 세션 초기화 시 비움)
- `_loadReceived`: 캐시 있음 > 즉시 표시 + 백그라운드 서버 재조회 / 캐시 없음 > `isReceivedLoading` 표시 후 조회
- 로딩 표시를 화면 카운터(`_activeLoadCount`)에서 상태 `isReceivedLoading`으로 이동 > 카드 전환·푸시 수신·mutation 후 재조회·당겨서 새로고침에서 캐시가 있으면 스피너 없음
- 서버 재조회 원칙 유지: 캐시는 표시용 시작값일 뿐, 모든 경로가 서버 재조회
- 무효화: 정렬 변경 > 전체 비움(스피너), 조회 실패 > 해당 카드 비움(기존처럼 실패 뷰), 카드 목록에서 빠진 카드 > 비움, 읽음 처리 > 캐시도 갱신
- 경쟁: 기존 차수(generation) 비교 유지. 오래된 응답은 상태·캐시 모두에 쓰지 않음

## 3. 요청 목록 지연 생성

- `RequestReceivedList`·`RequestSentList`를 sliver 위젯으로 변경, 화면 `CustomScrollView`에 직접 배치 (`SliverList.builder`)
- 등장 애니메이션: 앞쪽 항목(지연 상한 안 9개)만, 유지(keep-alive)로 스크롤 복귀 시 재생 안 함. 뒤쪽 항목은 애니메이션 없이 생성 (공통 `StaggeredListItemEntrance`)

## 4. 차단 회원 요청 제외

- 화면이 `memberBlockProvider` 구독 > 받은 요청은 요청자, 보낸 요청은 상대 물품 주인이 차단 목록이면 표시에서 제외 (상태는 그대로, 표시 파생 값. 해제 시 다시 표시)
- 파생 함수는 `TradeRequestsState`에 둠 (테스트 가능)

## 5. 채팅방 진입 병렬화

- 기존: 회원 ID > 소켓 연결 > 메시지 조회 > 읽음 상태 조회 (순차)
- 변경: 회원 ID(로컬 저장소, 실패 시 중단) > [소켓 연결, 메시지 조회, 읽음 상태 조회] 동시 시작 > 모두 끝난 뒤 기존 순서대로 반영·구독
- 실패 처리 동일: 하나라도 실패 > 기존 catch(오류 화면). `Future.wait`로 모든 호출에 리스너를 붙여 처리 안 된 비동기 오류 방지

## 6. 프로필 후기 주소

- 기존: 후기마다 순서대로 주소 변환 + 건마다 `setState` (로딩 표시는 전부 끝날 때까지 유지)
- 변경: `ReviewerAddressResolver`(서비스)가 주소 없는 작성자를 회원 ID로 중복 제거 > 병렬 조회(네트워크 동시 4개 제한·캐시는 `AddressLookupCache`가 담당) > 결과 맵 1회 반영
- 실패 건은 결과에서 빠짐(기존처럼 '(알 수 없음)')
